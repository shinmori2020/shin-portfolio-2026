## 人間（シン）にしかできないもの

### 1. 成果データ（outcomes） — 内容面で最も効く

`src/data/works.ts` の各作品に `outcomes` を書くと、詳細ページの「05 成果」が表示される。
**現在は全8件とも未入力**で、未入力の間はセクションごと非表示になる（表示は壊れない）。

未入力だと「作ったものの説明はあるが、それで何が良くなったかが無い」状態になる。
制作会社が最も見たい部分なので、ここが埋まると説得力が変わる。

自主制作でも書ける。実測値や仕様の要点で十分。書き方の記入例は works.ts 内の
コメントを参照（数値改善は before→after / 単発の実測値は after のみ / 定性成果は label+note）。

### 2. Gradientr の技術構成の確認 — 正確性の問題

`src/data/works.ts` の `gradientr` は **React + Vite** と記載しているが、これは推測。
公開ページの HTML が `<div id="root">` と Vite のビルド成果物だったことから判断した。
実際が違えば `stack` と `tags` を直す。

完成度ではなく**事実の正確性**の問題。技術的な話になった時に食い違うため、
ここだけは確認しておいた方が安全。

### 3. 独自ドメインの登録 — 任意・急がない

**運営への通知は正常に動いている**（2026-07-28 に実送信で確認済み）。残るのは自動返信のみ。

現在の送信元は Resend のサンドボックス（`onboarding@resend.dev`）で、この状態では
**Resend アカウント本人以外へ送ると必ず 403 になる**。そのため実際の訪問者への自動返信は
`src/app/actions/contact.ts` の判定でスキップされる（運営通知は届くので取りこぼしは無い）。

完了カードの文言は「1〜2営業日を目安に折り返します」であり、自動返信メールの
到着を約束していないため、未対応でも表示上の不整合は起きない。

**ドメイン契約が必要。** `shin-portfolio-2026.vercel.app` は Vercel 保有ドメインの
サブドメインなので DNS レコードを追加できず、SPF/DKIM を通せない。
費用の目安は `.com` で年 1,600〜2,000円。初年度だけ安い業者は更新料に注意。
Vercel で買うと DNS 設定が自動で済むぶん手間が少ない。

取得すると自動返信の有効化に加えて**サイトのURLも独自ドメインにできる**。
ポートフォリオとしては渡すURLが独自ドメインである方が印象が良いので、むしろこちらが主目的。

どちらも Vercel の環境変数に `NEXT_PUBLIC_SITE_URL` と `CONTACT_EMAIL_FROM`
（例: `シン <hello@自ドメイン>`）を追加するだけで、**コード変更は不要**。

## 任意の改善（実装側・急がない）

### 4. 作品詳細の表示速度

Render Delay が 1.7〜3.7秒と振れる。ヒーロー画像を包む reveal のフェード（0.75秒）が
そのまま LCP に乗るため、この1箇所だけ演出を外せば縮む。ただし見出しは動いて
画像だけ即出るため見た目の統一感は落ちる。表示をブロックする CSS（34KB）を削る手もある。

### 5. 本文側のタップ領域 — 17件

WCAG 2.2 の 24x24 に届いていない操作要素が本文側に残っている。

| 場所 | 内容 | 件数 |
|---|---|---|
| `/works` | 各カードのURLバー（外部リンク）16px | 8 |
| `/tech` | 資料へのリンク 20px | 6 |
| 各所 | ←トップへ戻る / ←Works / サイトを見る→ | 3 |

いずれも文字幅が100px以上あり横方向には十分なため、実害は小さい。
ヘッダー・フッター・同意チェックボックスは対応済み（2026-07-30）。

本文中に埋め込まれた「プライバシーポリシー」「お問い合わせフォーム」の2件は
WCAG 2.2 の「文中のリンク」除外規定に該当するため対応不要。

### 6. 作品詳細のURLバーをリンクにする

一覧ページではブラウザ枠のURLバーが公開サイトへの外部リンクだが、詳細ページでは
ただの文字になっている（外部リンクは上の「サイトを見る →」が担う）。

詳細のスクリーンショットは全体が `<button>`（クリックで全景モーダル）なので、
その内側にリンクを置くと `<button>` の中に `<a>` が入る不正な入れ子になる。
両立させるならモーダルの操作範囲を画像だけに限定し、URLバーを枠の外へ出す。

## 判断済み・対応しないもの

### `--faint` のコントラスト（WCAG AA 未達）— 現状維持と判断（2026-07-29）

`--faint` は AA の 4.5:1 に届いていない。ライト `#9b9d94` が 2.47:1 / ダーク `#6c726b` が 3.42〜3.87:1。
該当は 10.5〜13px の補助ラベル32要素（フッターの著作権表記 / 作品詳細の CLIENT・ROLE・YEAR /
フォームの「任意」バッジ / ブラウザ枠の URL 表記 / プライバシーの制定日）。

**直さない理由**: AA を満たす値（ライト `#6e6f69`）は既存の `--muted`（`#6b6e66`）とほぼ同色で、
「本文 → 補足 → ラベル」の3段階だった濃さの階層が2段階につぶれる。
余白とトーンで階層を作るこのサイトの設計と正面からぶつかるため、現状の見た目を優先した。

**前提**: 本文・見出し・リンク・ボタンはすべて基準を満たしている。最も深刻だった
ダークモードの主要CTA（白文字×明るい緑で 2.42:1）は `--on-accent` の導入で 7.91:1 に修正済み。
残るのは補助情報のみで「読めずに操作できない」状態は無い。

**再検討する時**: Lighthouse のスコアを上げたくなった時、または色の階層設計を見直す時。
文字を18px以上にすると基準が 3:1 に緩むが、ライトの 2.47:1 はそれも下回るため
サイズ変更だけでは足りず多少の色調整は要る。

## サイトの規約（作業時に守るもの）

- 文体: **読点「、」を使わない**（UI 文言）。半角スペースまたは文の分割で処理する
- 優先順位: 速度（LCP/INP/CLS） > 既存機能の無事 > 世界観（引き算） > 見た目の忠実度
- 完了条件: `tsc --noEmit` / `next lint` / `next build` の通過
- `.wrap-phrase`（文節での折り返し）は**数行で終わる短文にだけ**使う。
  長文に使うと行数が増えて右端が不揃いになり、語の途中で割れることがある
