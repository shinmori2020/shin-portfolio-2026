# Works スクリーンショット自動撮影（設計メモ）

Works 掲載サイトのスクリーンショットを Playwright で統一条件撮影する仕組みの設計メモ。運用手順は `scripts/README.md` を参照し、ここには**なぜその実装なのか**と**踏んだ落とし穴**を残す。

関連ファイル：

| ファイル | 役割 |
|---|---|
| `scripts/capture-list.mjs` | 撮影対象の案件リスト（人間が実URLを記入する設定側） |
| `scripts/capture-works.mjs` | 撮影本体（統一条件を固定。案件ごとの事情は list 側で吸収する） |
| `src/lib/workImages.ts` | `public/works/{slug}/cover.*` `full.*` を探索する解決層 |
| `src/components/common/WorkImageLightbox.tsx` | full があればライトボックス表示・無ければ導線ごと非表示 |

## 2種類の画像と役割分担

| 出力 | 撮り方 | 用途 |
|---|---|---|
| `cover.png` | ファーストビュー（`fullPage: false`） | 一覧カード・詳細ヒーロー・最新作カード |
| `full.png` | ページ全体（`fullPage: true`） | 詳細ページの「全体を見る」ライトボックス |

`capture-list.mjs` は slug ごとに2件（cover / full）を並べる。出力名は `out`（既定 `cover.png`）で切り替える。1ターゲット＝1スクリーンショットの単純な構造を保ち、両方を1回で撮る特殊化はしていない。

## 落とし穴1: fullPage 撮影で reveal 前の白紙が写る

### 症状

`fullPage: true` で撮ると、ファーストビューから下の広い範囲が**白紙**で写った（headless-wp-media = nordic-works）。見出しだけ出て、記事カード・特集カード・導入事例カードの中身が一切写らない。

### 原因

対象サイトの fade-in が **Framer Motion の `whileInView` を `once: true` 無しで実装**していた。この場合、要素はビューポートに入ると表示され、**出ると `opacity: 0` に戻される**。

`fullPage` はビューポート外までまとめて撮るだけで、スクロールしたことにはならない。よって画面外の要素は一度も発火せず `opacity: 0` のまま写る。

さらに厄介なのは、**撮影前に全体をスクロールしても解決しない**こと。スクロールで発火はするが、先頭へ戻した時点で下部が再びビューポート外になり、隠れ直してしまう。

診断で、先頭復帰後に残っていた9要素はすべて `opacity: 0; transform: translateY(16px)` のインラインスタイルを持ち、正体は記事/特集/導入事例のカードそのものだった。これが `whileInView` の署名である。

### 対策（2段構え）

`fullPage` の時だけ、撮影直前に以下を行う（`cover` は表示済みなので何もしない）。

1. **全体をゆっくりスクロールする** … 遅延読み込み（`loading=lazy`・クライアント取得）を誘発し、一度きりの reveal を発火させる
2. **隠れ直した reveal を最終状態へ確定する** … 「インラインで opacity がほぼ0 **かつ** transform 付き」という `whileInView` の署名を持つ要素だけを対象に、インラインスタイルを上書きする

条件を「opacity と transform の両方」に絞るのが要点。意図的に隠している要素（`display: none`、transform を持たないオーバーレイ等）を巻き込まないための線引きである。

### 不採用にした案：ビューポートを全高へ広げる

「ビューポート自体をページ全高にすれば全要素が入りっぱなしになり、隠れない」という案を実際に試したが**不採用**。

- `100vh` 指定のヒーローがビューポート高（5580px）まで**引き伸ばされ**、実際の見た目と別物になった
- しかも白紙は直らなかった
- 加えて Chromium のテクスチャ上限（約 16384 device px / DSF=2 なら CSS px で約 8192）に当たるリスクがある

ページの見た目を保ったまま撮る、という目的に反するため破棄した。

## 落とし穴2: この環境の npm は `-- <flag>` をスクリプトへ渡さない

`npm run capture -- --skip-existing` を実行しても、スクリプトの `process.argv` にフラグが**入らない**（`--list` でも同様に再現）。結果、既存を残すつもりが**全件再撮影**され、承認済みの `cover.png` を上書きしてしまった。

**フラグ付き実行は node を直接叩くこと。**

```bash
node scripts/capture-works.mjs --skip-existing
node scripts/capture-works.mjs --slug=headless-wp-media
```

フラグ無しの `npm run capture`（全件撮影）は問題なく動く。

なお `--skip-existing` の存在判定は cover 固定ではなく**ターゲットの `out` 単位**で行う。cover が既にあり full が無い時、cover はスキップして full だけ撮る、という運用ができる。

## 落とし穴3: reduce が背景アニメを「崩れた中間状態」で凍結する

### 症状

nordic-works のヒーローは水の波紋が流れる背景アニメを持つ。撮影すると、波紋が濃い輪郭の同心円状で止まり、重く目立って見出しの視認性を下げていた。

### 原因

統一条件の `reducedMotion: 'reduce'` が効き、サイト側の JS が `prefers-reduced-motion` を見てアニメーションループを停止していた。その結果、**たまたま止まった中間フレーム**が毎回写っていた。「登場アニメの途中を写さない」ための設定が、常時動く背景アニメでは逆に働いた形である。

### 対策

案件ごとに `reducedMotion: 'no-preference'` で上書きできるようにした。既定は `reduce` のままなので、他案件の登場アニメ対策は維持される。

### 重要: この案件の絵は再現しない

波紋は `<canvas>` に `requestAnimationFrame` で描画されている（CSS/WAAPI のアニメーションは0件）。そのため**撮影ごとに違うフレームが撮れる**。以下はいずれも再現に失敗した。

- `waitMs` で待つ … アニメがページ読み込みと同期しておらず、待っても撮れる瞬間はバラバラ
- Playwright の仮想時計（`page.clock`）で時間を固定 … 同一指定でもハッシュ不一致

したがって**この案件は「撮り直すたびに絵が変わる」前提で扱う**。採用要件は「同じ絵柄であること」ではなく **円形が崩れて淡いこと**（人間の判断）。撮り直した際は目視確認し、気に入らなければ再実行する。

現行画像は6枚撮って、ヒーロー領域の暗部率（暗いピクセルの割合）が最小のものを採用した（7.4% → 1.9%）。

## 落とし穴4: `clip` を `fullPage` 無しで渡すと1画面しか撮れない

### 症状

横に溢れたページ対策で `clip` を渡したところ、全景のつもりの `full.png` が
ビューポートと同じ 2880x1800 で保存された（web-creation-service）。cover と見分けがつかない。

### 原因

`page.screenshot({ clip })` は `fullPage` を伴わないと、`clip` がビューポート内へ切り詰められる。
ドキュメント座標で高さ 8549px を指定しても、実際に撮れるのは先頭の 900px だけになる。

### 対策

**`clip` と `fullPage` は併用する。** 両立できないと思い込まないこと（実際に併用可能）。

```js
await page.screenshot({ path, fullPage: true, clip: { x: 0, y: 0, width: 1440, height: scrollHeight } });
```

### 横溢れの切り出しはなぜ要るか

`fullPage` は `scrollWidth` 全体を撮る。横スクロールが発生するサイトでは画面外の余白まで写り、
右側が間延びした絵になる（web-creation-service は 4344px 幅で撮れていた）。
`computeFullClip()` が「溢れている時だけ」ビューポート幅で切る。溢れていなければ何もしない。

## 落とし穴5: `content-visibility` で画面外が未描画のまま写る

### 症状

`full.png` の上2カテゴリ以降が、**枠だけあって中身が無いカード**で埋まった（web-parts-reference）。
白紙ではなく「輪郭は正しいが文字が無い」のが特徴。

### 原因

`content-visibility: auto` が 200 要素に設定されていた。画面外の要素の描画を丸ごと省き、
実寸の代わりに `contain-intrinsic-size` の箱だけを確保する高速化手法である。
`fullPage` はビューポート外まで一度に撮るため、この空の箱がそのまま写る。

落とし穴1の reveal と同じく、**スクロールで一度描画させても画面外へ戻ると再びスキップされる**。
スクロールだけでは解決しない。

### 対策

撮影中だけ無効化する。`disableContentVisibility()` が該当要素の有無を調べ、
1つでもあれば `*{content-visibility:visible !important}` を注入する。

**高さが実寸に変わるため、`clip` の計測より先に実行すること。** 順序を誤ると切り出し位置がずれる。

## 落とし穴6: スクロール連動スライダーの余白が白紙で写る

### 症状

`full.png` の末尾 3923px が真っ白になった（slider-patterns）。

### 原因

最後のスライダー（フルスクリーン縦スクロール）が
**「4500px のスクロール余白 + 900px の `position: sticky` パネル」** という構成だった。
余白はスクロール量を稼ぐためだけのもので中身が無い。
実際に触っている間は sticky パネルが貼り付いてスライドが切り替わるので気づかないが、
静止画にすると余白がそのまま白紙になる。

これは落とし穴1や5と違い、**描画を復元する手段が無い**。余白には元から何も無いため。

### 対策

`fullHeightUntil` に sticky パネルのセレクタを渡し、その下端で `fullPage` を打ち切る。

```js
const SLIDER = { url: '...', fullHeightUntil: '.slider-fullscreen' };
```

slider-patterns は 10438px → 6515px になり、スライダー07 の1画面目までを見せて余白を落とせた。
「セクションの何割まで」ではなく**実際に描画される要素の下端**を指定するのが要点。
サイト側の上流セクションの高さが変わっても追従する。

## 案件ごとの逃げ道（capture-list のオプション）

統一条件は `capture-works.mjs` に固定し、**案件ごとの事情はすべて `capture-list.mjs` で吸収する**。
本体を書き換えないこと。

| オプション | 用途 | 実例 |
|---|---|---|
| `dismiss` | クリックして閉じる（Cookie バナー・初期モーダル） | nordic / proposal-builder |
| `hide` | クリックでは閉じられない固定要素を `display:none` にする | web-creation-service |
| `waitMs` | 遅延読み込み・演出の頃合い待ち | 全案件で調整 |
| `fullPage` | 縦長全景を撮る | full.png 側 |
| `fullHeightUntil` | 全景をこの要素の下端で打ち切る | slider-patterns |
| `reducedMotion` | 常時動く背景アニメの凍結回避 | nordic / slider-patterns |

### `dismiss` と `hide` の使い分け

**押すと閉じるものは `dismiss`、押すと開いてしまうものは `hide`。**

web-creation-service の右下に出るチャットボット（`#chatbot`）は、クリックすると閉じるどころか
**展開する**。`dismiss` では消せない。固定配置のため `fullPage` ではヒーローに焼き込まれ、
一覧サムネと全景で見え方もずれる。表示ごと落とすのが確実である。

## Cookie バナーの扱い

`dismiss` に閉じるボタンのセレクタを書くと、撮影前にクリックして閉じる。

`dismiss` は Cookie バナーに限らず、**初期表示で本体を覆うモーダル全般**に使う。

- 4案件を調査した結果、**Cookie バナーが出るのは nordic-works のみ**。他3案件には書いていない（存在しないセレクタを書くと毎回「見つからず」の警告が出るだけで無意味なため）
- proposal-builder は初回に「業種テンプレートを選択」モーダル（`z-50` の全画面オーバーレイ）が出て UI 本体が隠れるため、`text=キャンセル` で閉じてから撮る。`role="dialog"` は付いていないので Esc では閉じられず、閉じるボタンの指定が要る
- 閉じ方は **「拒否する」** を採用。撮影目的では見た目に差が無く、不要な同意を残さないため
- `cover` / `full` の**両方**に適用している。片方だけ消すと、一覧サムネにはバナーがあるのに全体表示では無い、という食い違いが起きる

full では特に重要で、バナーは固定配置のためページ中腹に焼き込まれ、「最新の記事」の見出しに重なっていた。

## ライトボックスのフォールバック

`WorkImageLightbox` は `full` がある時だけクリック可能にし、「全体を見る」のヒントとモーダルを出す。**`full` が無い案件では導線ごと出さない**（静的なブラウザ枠のみ）。

cover へフォールバックして「全体を見る」を出すと、開いてもファーストビューが出るだけで期待を裏切るため、導線自体を消す判断とした。画像規約（`public/works/README.md`）の「置くだけで反映・無ければ自動フォールバック」の思想に沿っている。

### 1画面完結のページは `full` を撮らない

gradientr は `scrollHeight` がビューポートと同値（1440x900）の1画面完結 UI で、
全景を撮っても cover と同じ絵になる。**撮影対象から外し、`full.webp` を置かない。**

上記のフォールバック方針により「全体を見る」の導線ごと消えるため、
開いてファーストビューが出るだけ、という期待外れを避けられる。

撮る前に `scrollHeight` を確認し、ビューポート高と同じなら `full` の行を追加しないこと。

## WebP 化（対応済み）

全要素が描画されるようになった分 `full.png` は重くなり、特に headless-wp-media は約9.9MB あった。ライトボックスを開いた時に実際に読み込まれるため、表示速度を優先する本サイトの方針に反する。

`scripts/to-webp.mjs` で cover / full の8枚すべてを WebP へ変換した。画像規約（`src/lib/workImages.ts`）は `webp` を最優先で探索するため、**置き換えるだけでコード変更は不要**。

```bash
node scripts/to-webp.mjs              # 変換のみ（PNG を残して画質を確認したい時）
node scripts/to-webp.mjs --delete-png # 変換後に元 PNG を削除
```

### 実績（quality=80 / effort=6）

| 画像 | 変換前 | 変換後 | 削減 |
|---|---|---|---|
| headless-wp-media/full | 9,626 KB | 970 KB | -89.9% |
| headless-wp-media/cover | 1,578 KB | 83 KB | -94.8% |
| multilingual-ec/full | 1,346 KB | 326 KB | -75.8% |
| multilingual-ec/cover | 718 KB | 32 KB | -95.5% |
| **合計（8枚）** | **14,685 KB** | **1,868 KB** | **-87.3%** |

削減率が極端に高いものは、UI のベタ塗り・グラデーションに対して PNG が非効率だったため。等倍で目視確認し、細線のロゴ・日本語の文字・写真のディテールいずれも劣化は認められなかった。

### WebP には 16383px の上限がある

縦長ページの `full` はこれを超える。実例は 20876px（slider-patterns の修正前）で、
変換が `Processed image is too large for the WebP format` で落ちた。

`to-webp.mjs` は超過した時だけ長辺を 16000px へ縮小する（`MAX_EDGE`）。
上限内の画像は素通しなので、既存の変換結果は変わらない。

なお落とし穴6 の対処で余白を落とすと、そもそも上限に当たらなくなることがある。
**縮小が入るより打ち切りで短くする方が、結果として解像度は高くなる。**

### 運用メモ

- **PNG は残さない**。`webp` が優先探索されるため PNG は永遠に未使用となり、リポジトリを膨らませるだけになる
- 撮影スクリプトの出力は PNG のまま（撮影と変換は別工程）。**再撮影したら変換もやり直す**
- 画質を疑う時は `--delete-png` を付けずに実行し、PNG と並べて比較してから削除する
- **撮ったら必ず目視する**。落とし穴4〜6 はいずれも「撮影は成功し、ファイルも生成される」ため、
  ログだけでは気づけない。cover と full を1枚ずつ開いて確認すること
